## 一、非功能需求（NFR）

### 1. 性能需求（容量与响应，MVP 基准值，非对外承诺）
| 编号 | 指标 | 目标值 | 说明 |
| --- | --- | --- | --- |
| NFR-P1 | 可售查询接口响应 | P95 ≤ 300ms | 走索引 + 房型缓存；区间库存查询命中 `uk_type_date` |
| NFR-P2 | 创建订单接口响应 | P95 ≤ 800ms | 含事务内逐夜扣减；典型订单 ≤3 间、≤7 夜 |
| NFR-P3 | 吞吐能力（单实例） | 查询 ≥100 QPS、下单 ≥20 TPS | 演示/课程基准，上线前以压测为准 |
| NFR-P4 | 并发正确性 | 任意并发下**零超卖、无负库存** | 条件 UPDATE + 事务；见 AC-02 |
| NFR-P5 | 数据库 | 关键查询走索引，禁止全表扫描落在订单/库存表 | 慢 SQL 阈值 1s |

### 2. 并发与一致性
- 库存扣减/回滚、订单创建/取消、入住/退房均在**数据库本地事务**内完成；
- 防超卖以数据库**条件更新的影响行数**为最终裁决，Redis 锁仅作热点前置，不承担正确性；
- 支付回调、超时取消等异步/重复消息通过**唯一键 + 状态机**保证幂等；
- 订单状态流转在 Service 层集中校验，拒绝非法跳转。

### 3. 安全需求
| 类别 | 要求 |
| --- | --- |
| 认证 | 无状态 JWT，有效期默认 2 小时；登出/失效由前端丢弃令牌 + 服务端黑名单（迭代，可用 Redis） |
| 授权 | RBAC 三类角色，接口级鉴权；会员只能操作本人订单（越权返回 403） |
| 密码 | 加盐哈希存储（骨架为 SHA-256+随机盐可运行示例，**生产必须替换为 BCrypt/Argon2**），禁止明文、禁止日志输出 |
| 敏感数据 | 身份证号、手机号在列表/日志中脱敏；身份证生产应加密存储 |
| 传输 | 生产环境全站 HTTPS（Nginx 配置 TLS） |
| 注入防护 | MyBatis 参数绑定防 SQL 注入；输出转义/入参校验防 XSS |
| 接口防护 | 登录/短信验证码接口限流（迭代，Redis 计数）；错误响应不返回堆栈与内部路径 |
| 数据隔离 | MySQL/Redis 端口不对公网暴露；最小权限数据库账号 |

### 4. 可靠性与可用性
- 应用无状态（状态存 MySQL/Redis/JWT），可直接水平扩容多实例 + Nginx 负载均衡；
- MVP 单实例目标可用性 **99.5%**（教学/演示）；正式运营建议 99.9%（对应手册 SLA：年停机 ≤8.76h）；
- 建议 SLO：API P95 ≤500ms、错误率 <0.5%、库存一致性事故 = 0；
- MySQL 每日 02:00 逻辑备份保留 30 天；关键变更前手动备份。

### 5. 兼容性与可维护性
- 后端：JDK 17、Spring Boot 3.2、MySQL 8.0、Redis 7；Maven 3.6+；
- 接口：REST + JSON，字符集 UTF-8；管理后台兼容 Chrome/Edge 最近两个大版本；
- 配置：环境分离（`application-dev.yml` / `application-prod.yml`），数据库口令等通过环境变量注入，不写死进代码库；
- 代码：统一分层、统一返回、统一异常、统一日志；依赖在 `pom.xml` 锁定精确版本（手册依赖管理原则）。

### 6. 可观测性
- 统一访问日志与错误日志（traceId 串联一次请求，迭代）；
- 暴露 `GET /api/health` 健康检查；后续接入 `spring-boot-starter-actuator` + Prometheus + Grafana；
- 告警建议：CPU>80%、磁盘>85%、应用进程存活、下单错误率突增、定时任务未执行。

## 二、部署方案

### 1. 环境依赖清单
| 组件 | 版本 | 用途 |
| --- | --- | --- |
| OS | CentOS 7+/Ubuntu 20.04+ | 服务器操作系统 |
| JDK | 17（仅手工部署需要） | 运行 Spring Boot |
| Docker / Compose | 20.10+ / v2+ | 容器化部署（推荐） |
| MySQL | 8.0 | 业务数据库 |
| Redis | 7.x | 令牌/缓存/锁（MVP 可先不强制） |
| Nginx | 1.20+ | 反向代理、HTTPS、静态资源 |

### 2. 服务器配置建议
| 环境 | 配置 | 部署内容 |
| --- | --- | --- |
| 开发/演示 | 2 核 4G、磁盘 40G | 单机 docker-compose 拉起全部容器 |
| 生产（小型酒店） | 4 核 8G、磁盘 100G SSD | 应用 + Redis 同机；建议 MySQL 用云数据库 RDS 或独立主机并定时备份 |

### 3. 部署方式 A：Docker Compose（推荐，一键起）
仓库提供容器化文件：`backend/Dockerfile`、`deploy/docker-compose.yml`、`deploy/nginx.conf`、`deploy/.env.example`。
步骤：
```bash
# 1) 准备部署目录，复制 backend/ 与 deploy/
# 2) 配置环境变量
cp deploy/.env.example deploy/.env      # 修改数据库 root/业务账号密码、JWT 密钥
# 3) 构建并启动（首次会构建应用镜像、初始化 MySQL）
docker compose -f deploy/docker-compose.yml up -d --build
# 4) 初始化数据库（仅首次；容器内 MySQL 已就绪后执行）
docker exec -i <mysql容器> mysql -uroot -p"$ROOT_PWD" < database/schema.sql
docker exec -i <mysql容器> mysql -uroot -p"$ROOT_PWD" < database/seed.sql
# 5) 验证
curl http://服务器IP/api/health
```
- compose 编排 4 个服务：`nginx(80/443) -> hotel-app(8080) -> mysql(3306, 仅内网) / redis(6379, 仅内网)`；
- MySQL、Redis 数据通过命名卷持久化；**端口不对公网暴露**。

### 4. 部署方式 B：手工部署（无 Docker）
```bash
# 1) 安装 JDK17、MySQL8、(可选)Redis7
# 2) 初始化数据库
mysql -uroot -p < database/schema.sql
mysql -uroot -p < database/seed.sql
# 3) 修改配置（数据源账号密码、JWT 密钥、profile=prod）
#    可用环境变量：SPRING_DATASOURCE_URL / SPRING_DATASOURCE_USERNAME / SPRING_DATASOURCE_PASSWORD / APP_JWT_SECRET
# 4) 打包
cd backend && mvn clean package -DskipTests
# 5) 启动（建议用 systemd 或 nohup 守护）
java -jar target/hotel-booking-1.0.0.jar --spring.profiles.active=prod
# 6) Nginx 反代 /api 到 127.0.0.1:8080，配置域名与 TLS 证书
```
停止：`kill <pid>` 或 `systemctl stop hotel-booking`。

### 5. 回滚方案（对应手册"回滚步骤"）
- 应用镜像/制品按版本号保留最近 3 个版本（如 `hotel-booking:1.0.0`）；
- 回滚：`docker compose` 切回上一镜像 tag 重启，或 `java -jar` 上一版本 jar；
- 数据库变更遵循 Flyway"只增不破坏性变更"原则；涉及表结构变更的上线必须附带**回滚 SQL**并在发布前演练；
- 发布失败且影响服务时，先回滚应用恢复可用，再排查问题。

## 三、日常运维要点（Runbook 摘要）
- **日常巡检**：应用进程/健康检查、CPU/内存/磁盘、容器状态、错误日志、定时任务（超时取消）是否执行、MySQL 连接数与慢查询；
- **常见故障定位顺序**：① `docker compose ps`/进程是否存活 → ② 应用日志 → ③ 应用到 MySQL/Redis 连通性 → ④ 磁盘/连接数 → ⑤ 重启应用；
- **备份恢复**：每日 mysqldump，保留 30 天；定期做一次恢复演练（备份不可用=没有备份）；
- **容量规划**：当 CPU 持续 >70% 或下单 TPS 接近上限，增加应用实例；库存/订单表数据增长后按日期做归档与分区评估；
- **安全运维**：及时打系统/依赖补丁、定期依赖漏洞扫描、最小权限、生产默认账号上线即改密。
