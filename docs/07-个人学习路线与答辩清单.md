## 四、三门课分别需要掌握的内容

### 1. 软件工程

你需要理解一个软件项目如何从想法变成可验证系统。

必须掌握：

- 需求：系统为谁服务，解决什么问题。
- 范围：本期做什么，不做什么。
- 设计：系统分为哪些模块，模块之间如何调用。
- 接口：前后端通过什么数据约定协作。
- 测试：正常流程、边界和异常如何验证。
- 风险：超卖、重复支付、时间日期错误和权限越权。
- 追溯：一条需求如何落到接口、代码和测试。

需要能够解释：

- 为什么先确定需求和接口，再开发页面。
- 为什么测试不能只测“成功流程”。
- 为什么需求、设计、代码和测试必须保持一致。

### 2. 高级程序设计

重点不是语法背诵，而是说明为什么这样设计 Java 程序。

必须掌握：

- Spring Boot 启动类和依赖注入。
- Controller、Service、Mapper 的分工。
- Entity、DTO、VO 的区别。
- 接口与实现类解耦。
- 参数校验和统一异常处理。
- JWT 登录和角色权限。
- 事务边界和条件更新。
- Java 时间类型：LocalDate、LocalDateTime。
- Stream、集合和分组统计的基础使用。
- 并发请求下为什么不能“先查询再修改”。

需要能够解释：

- 为什么业务规则放在 Service，而不是 Controller。
- 为什么数据库实体不能直接当作所有接口的返回对象。
- 为什么 @Transactional 不能脱离数据库事务单独生效。
- 为什么多条库存扣减必须属于同一个事务。

### 3. 数据库

重点掌握“数据怎么组织”和“并发时怎么保证正确”。

必须掌握：

- 实体关系图和表之间的一对多、多对一关系。
- 主键、唯一键、普通索引和逻辑外键。
- 按夜库存表为什么以“房型 + 日期”作为核心维度。
- 半开区间 [入住日, 离店日)，离店当天不占库存。
- SELECT、INSERT、UPDATE、JOIN、聚合和排序。
- 事务的原子性：整单成功或整单回滚。
- 条件 UPDATE 防止库存扣成负数或超卖。
- 唯一约束和状态检查实现支付回调幂等。
- 索引为什么不能等同于外键，二者解决不同问题。

需要能够解释：

- 为什么不把库存只保存成房型表中的一个数字。
- 为什么下单成功后，订单和库存必须一起提交。
- 为什么同一笔支付回调重复到达不能重复确认订单。

## 五、必须掌握的六条核心业务链路

### 链路 1：登录与权限

流程：

1. 会员提交手机号、密码和昵称完成注册，或提交手机号和密码登录。
2. 后端查询 user 表。
3. 校验加盐哈希后的密码。
4. 生成 JWT，返回角色。
5. 前端保存 Token。
6. 后续请求携带 Token。
7. 拦截器解析 Token 并校验角色。

你要能说明会员、前台、管理员分别能访问什么。

### 链路 2：房型与可售查询

流程：

1. 前端提交入住日和离店日。
2. 后端校验离店日必须晚于入住日。
3. 系统遍历 [入住日, 离店日) 的每个夜晚。
4. 每晚可售量等于 total_count 减 booked_count。
5. 一个房型的可订量取区间内每晚可售量的最小值。
6. 任意一晚无库存，该房型整体不可订。

例子：

入住 9 月 25 日，离店 9 月 27 日，占用 9 月 25 日和 9 月 26 日两个夜晚，不占用 9 月 27 日。

### 链路 3：创建订单与防超卖

流程：

1. 校验日期、房型和数量。
2. 计算每晚房价和订单总额。
3. 按房型合并相同明细。
4. 对每个住宿夜晚执行条件 UPDATE。
5. 只有剩余库存不少于请求数量时才扣减成功。
6. 任意一晚扣减失败，整个事务回滚。
7. 订单主表和订单明细表同时写入。

防超卖核心条件：

    WHERE total_count - booked_count >= 请求数量

不能采用下面这种不安全方式：

1. 先查询库存充足。
2. 再执行普通更新。

因为两个并发请求可能同时查到“剩 1 间”，最后都成功。

### 链路 4：支付与幂等

流程：

1. 会员为待支付订单发起支付。
2. 系统创建 INIT 状态的支付流水。
3. 支付回调到达后，根据支付单号找到流水。
4. 已成功的回调直接返回，不重复确认订单。
5. 同一交易号只能对应一笔有效支付。
6. 支付成功后订单从 PENDING_PAYMENT 变为 CONFIRMED。
7. 回调失败不能把订单错误地改成已确认。

### 链路 5：前台排房与入住

流程：

1. 前台查询已确认订单。
2. 系统显示 VC 空闲房间。
3. 为每条订单明细选择同房型房间。
4. 校验房间状态、房型匹配和日期冲突。
5. 回填订单明细的房间号。
6. 房间变为 OC 在住。
7. 订单变为 CHECKED_IN。

### 链路 6：退房与房态释放

流程：

1. 前台对在住订单办理退房。
2. 订单变为 COMPLETED。
3. 房间变为 VD 待清洁。
4. 清洁完成后人工把 VD 改为 VC。
5. 只有 VC 房间才可再次排房。

## 六、必须记住的订单状态

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| PENDING_PAYMENT | 待支付 | 支付或取消 |
| CONFIRMED | 已支付确认 | 前台排房 |
| CHECKED_IN | 已入住 | 办理退房 |
| COMPLETED | 已完成 | 流程结束 |
| CANCELLED | 已取消 | 流程结束 |
| REFUNDING | 退款中 | 后续退款完成 |
| REFUNDED | 已退款 | 流程结束 |

不要只背状态名。你要说明每一步由谁触发，数据库哪张表发生变化。

## 十、答辩问题与回答框架

### 问题 1：为什么选择 Java 和 Spring Boot？

回答框架：

- 课程要求 Java。
- Spring Boot 能快速完成 REST 接口、依赖注入和事务管理。
- 项目采用单体分层，适合当前规模和学习目标。
- 不使用微服务是为了避免超出课程范围和维护成本。

### 问题 2：系统整体架构是什么？

回答：

- 前端是 Vue 3 单页应用。
- 后端是 Spring Boot 单体应用。
- 数据层使用 MyBatis-Plus 和 MySQL。
- 后端按 auth、user、room、reservation、payment、pms 划分业务模块。
- 前端通过 REST API 调用后端，后端通过 Mapper 访问数据库。

### 问题 3：怎么防止超卖？

回答：

- 不能先查询再修改。
- 每个住宿夜晚执行带条件的 UPDATE。
- 条件要求剩余库存大于等于请求数量。
- 受影响行数为 0 表示该夜库存不足。
- 任意夜晚失败都会让整个事务回滚。

### 问题 4：怎么保证订单和库存一致？

回答：

- 创建订单和扣减库存放在同一事务。
- 订单明细按一间房一行保存。
- 取消或超时释放库存时也使用事务。
- 库存回滚条件要求 booked_count 足够，防止扣成负数。

### 问题 5：支付回调重复怎么办？

回答：

- 支付单状态为 SUCCESS 时直接返回，不重复处理。
- 交易号有唯一性约束和重复检查。
- 订单确认过程也检查当前状态。
- 因此重复请求不会重复增加库存或重复确认。

### 问题 6：为什么使用逻辑外键？

回答：

- 项目通过应用层和索引维护关系。
- 便于单体项目开发、初始化和数据迁移。
- 关系仍然在 DBD 和代码中明确。
- 如果正式生产，可以进一步评估物理外键和约束策略。

### 问题 7：日期为什么使用 [入住, 离店)？

回答：

- 酒店按夜销售，离店日不占当晚库存。
- 半开区间让跨月和天数计算更稳定。
- 可直接用“日期小于离店日”查询住宿夜晚。

### 问题 8：项目有哪些不足？

回答方向：

- 真实支付、短信和通知未接入。
- 当前重点是单体课程项目，不是高并发生产系统。
- Redis、缓存和更多自动化测试属于后续扩展。
- 当前先保证核心业务正确、可运行、可解释。

## 十三、房型图片与客户评论

### 房型图片如何展示

1. room_type 表中保存 cover_image 路径。
2. 图片文件放在 frontend/public/images/rooms 目录。
3. 可售查询接口同时返回 cover_image、description、average_score 和 review_count。
4. 前端根据返回字段展示图片、简介、评分和评论数量。

答辩时可以说：图片路径属于房型数据，图片文件作为前端静态资源本地保存，不依赖外网访问。

### 客户评论如何查询

1. review 表保存订单、会员、房型和评分。
2. 查询时只读取 status 为显示的评论。
3. 平均分使用 AVG(score)。
4. 评论数使用 COUNT(*)。
5. 评论列表通过 room_type_id 查询，并按创建时间倒序排列。
6. 评论接口为公开接口，未登录用户也可以查看。

答辩时可以说：房型列表展示聚合评分，点击查看评论后再分页读取详细评论，避免列表一次加载过多数据。
