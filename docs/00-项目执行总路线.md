# 酒店客房预订系统执行总路线

> 状态基线：2026-09-22  
> 用途：统一“文档理解、后端补全、前端实现、测试、部署、答辩”的先后顺序。  
> 规则：`docs/01` 至 `docs/05` 是设计与契约依据；本文件规定执行顺序与完成门槛；代码是最终事实。

## 一、最终交付目标

完成后应具备一套可演示、可解释、可重复运行的完整 Web 项目：

1. 数据库可一键初始化，后端可稳定启动。
2. 会员可注册、登录、查询房型、查询可售、下单、Mock 支付、查看订单、取消订单。
3. 前台可查看房态、排房入住、退房、修改房态。
4. 管理员可维护房型、房间和库存。
5. 前端覆盖会员、前台、管理员三类角色。
6. 核心业务有正常、边界、异常和并发测试证据。
7. 可在本地或服务器部署，并有演示与答辩材料。
8. 每项关键功能都能从“需求 → API → 代码 → 测试”追根溯源。

## 二、范围冻结

### 本项目必须完成

- 认证与 RBAC：MEMBER、RECEPTIONIST、ADMIN。
- 客房查询：房型、房间、按夜库存、区间可售。
- 预订主链：建单、事务扣库存、防超卖、取消、超时释放。
- Mock 支付：发起支付、回调确认、重复回调幂等。
- 前台 PMS：房态盘、排房入住、退房、房态维护。
- 管理后台：房型、房间、库存基础维护。
- 一套响应式 Web 前端，覆盖三类角色。
- 接口测试、核心业务测试、并发防超卖测试。
- 部署说明、演示脚本、答辩说明。

### 本项目暂不追求

- 真实微信/支付宝对接。
- 动态房价、评价、短信、复杂会员积分。
- 微服务、分布式事务、Redis 强依赖。
- 原生 App 或 uni-app 多端发布。

以上内容可以作为“后续扩展”介绍，但不能阻塞主项目交付。

### 阶段 1：理解需求与设计契约

**阅读顺序固定为**

1. `docs/01-产品需求文档-PRD.md`：角色、用户故事、功能范围、业务规则、AC。
2. `docs/02-概要设计-HLD.md`：分层、模块、技术选型、并发与技术决策。
3. `docs/03-数据库设计-DBD.md`：实体关系、按夜库存、可售与冲突 SQL。
4. `docs/04-接口设计-API.md`：URL、鉴权、入参、响应、错误码。
5. `docs/05-非功能需求与部署方案.md`：性能、安全、可靠性和部署约束。

**学习产物**

- 每个核心业务规则能回答：它解决什么问题、由哪张表、哪个 Service 和哪个 API 落地。
- 能解释“按夜库存”和“普通商品库存”的区别。
- 能解释建单为什么必须使用事务和条件更新来防止超卖。
- 能解释订单状态机的合法流转。

**阶段门槛**

- 能不看代码讲清一条完整预订链路。
- 能指出每项关键功能对应的 PRD 编号、API 和数据库表。

### 阶段 2：后端契约补全与自动化验证

**执行顺序**

1. 认证：注册、登录、Token、角色权限、公开接口。
2. 房型与库存：房型查询、房间、库存初始化、区间可售。
3. 预订：参数校验、计价、条件扣库存、事务回滚。
4. 支付：发起支付、回调、幂等、超时取消。
5. 取消：待支付取消、已支付退款状态、免费取消限制。
6. PMS：房态盘、排房冲突、入住、退房、房态维护。
7. 管理端：房型、房间、库存维护。

**必须补的验证**

- 固定数据库测试数据。
- API 冒烟脚本或集成测试。
- 并发防超卖测试：同一夜仅剩 1 间，多个请求同时下单只能成功 1 单。
- 时间边界：跨天、跨月、离店等于入住次日。
- 权限边界：MEMBER、RECEPTIONIST、ADMIN 互相越权的响应。

**阶段门槛**

- `docs/06` 中 AC-01 至 AC-08 有可重复的测试结果。
- 无未处理的 TODO、占位实现或与 API 文档冲突的接口。

### 阶段 3：前端基础工程

**技术路线**

- Vue 3 + Vite。
- Vue Router + Pinia + Axios。
- Element Plus。
- 先做一个 SPA，按角色显示会员端、前台端和管理员端入口，避免同时维护多套前端。

**执行顺序**

1. 工程初始化、环境变量、代理与统一请求封装。
2. 登录态、Token 保存、路由守卫、角色守卫。
3. 公共布局、菜单、表格、表单和错误提示。
4. 统一处理业务码、401 和 403。

**阶段门槛**

- 前端可以登录三类账号并按角色进入正确首页。
- 刷新页面不会丢失登录态。

### 阶段 4：会员端完整预订链路

**页面顺序**

1. 房型列表与筛选。
2. 日期与可售查询。
3. 房型详情与下单表单。
4. 支付页与 Mock 支付回调。
5. 我的订单、订单详情、取消订单。

**阶段门槛**

- 浏览器中能完成“查询 → 下单 → 支付 → 查看订单”完整流程。
- 页面错误提示与后端错误码一一对应。

### 阶段 5：前台与管理端

**前台顺序**

1. 房态盘。
2. 订单查询与排房。
3. 入住与退房。
4. 房态修改。

**管理端顺序**

1. 房型新增和修改。
2. 房间新增。
3. 库存初始化与补齐。
4. 基础查询与操作结果反馈。

**阶段门槛**

- 会员下单后，前台能完成排房、入住、退房。
- 管理员能通过页面新增房型、房间并补齐库存。

### 阶段 6：端到端测试与质量收口

**顺序**

1. 主流程回归。
2. 边界与异常回归。
3. 并发防超卖。
4. 权限与安全。
5. 浏览器端关键流程。
6. 数据一致性检查。

**阶段门槛**

- 新环境可按 README 从零启动。
- 核心用例全部通过，失败项有明确原因和处理结论。
- 不存在明显的前后端接口漂移。

### 阶段 7：部署与交付

**顺序**

1. 本地手工部署复验。
2. 配置外置化与敏感信息检查。
3. Docker/Nginx 方案复验（环境允许时）。
4. 数据库初始化、升级、备份和回滚说明。
5. 提供演示数据重置脚本。

**阶段门槛**

- 其他人可以按文档启动并复现主要流程。
- 演示前可以快速恢复到干净、稳定的数据状态。

### 阶段 8：答辩准备

**顺序**

1. 准备 5 分钟演示脚本。
2. 准备架构图与核心时序讲解。
3. 准备“需求 → 表 → API → 代码 → 测试”的追踪表。
4. 准备常见问题：为什么按夜库存、如何防超卖、如何保证幂等、为什么选择当前技术栈。
5. 对每项功能亲自操作一次、解释一次、故意制造一次错误并定位一次。

**阶段门槛**

- 不看稿可以完整演示。
- 老师随机指向一个页面或接口，能够讲清其上下游和关键代码。

## 四、每个功能统一执行顺序

后续新增任何功能，都按以下顺序推进：

1. 在 PRD 中确认规则和验收标准。
2. 在 DBD 中确认数据是否需要变化。
3. 在 API 文档中确认输入输出和错误码。
4. 实现或修正数据库脚本。
5. 实现后端并补测试。
6. 实现前端并接真实接口。
7. 做正常、边界、异常验证。
8. 更新演示与答辩材料。

禁止先写页面、再猜接口，或为了显示功能而绕开业务规则。
