## 1. 产品概述

### 1.1 产品定位
面向单体酒店/小型连锁酒店的客房预订与前台管理系统，包含两个使用端：

- **宾客预订端（C 端，H5/小程序/公众号，后续迭代）**：会员在线查可用房、预订、支付、查看订单、取消。
- **酒店管理后台（PMS，PC Web）**：前台与管理员管理房型、房间、房态、订单，办理入住/退房。

本期"基础架构"优先交付**后端服务 + 数据库 + 接口**，前端在后续迭代接入。

### 1.2 业务目标（对应 BRD 要点，简述）
- 线上化预订，减少电话/到店预订的人工成本与差错；
- 按"夜"售卖客房，**杜绝同一房间在同一日期区间被重复售卖（超卖）**；
- 沉淀会员与订单数据，为后续收益管理（动态房价）打基础。

### 1.3 核心痛点
- 客房是**按日期区间售卖的库存**，与普通电商"一件商品卖一次"不同，人工排房极易在旺季超卖；
- 房态（空闲/在住/维修/清洁）与订单状态不同步，前台容易开错房；
- 取消、No-show（未到店）、改期缺乏统一规则，造成可售房浪费或纠纷。

## 2. 角色与用户画像（Persona）

### 2.1 系统角色
| 角色 | 标识 role | 入口 | 核心职责 |
| --- | --- | --- | --- |
| 游客 | GUEST（未登录） | C 端 | 浏览房型、查询可用房与价格 |
| 会员 | MEMBER | C 端 | 预订、支付、查看/取消订单、评价 |
| 前台接待员 | RECEPTIONIST | PMS 后台 | 排房、办理入住/退房、处理订单、维护房态 |
| 系统管理员 | ADMIN | PMS 后台 | 房型/房间/房价/员工账号管理、数据统计 |

### 2.2 典型用户画像
**画像一：计划性出行的会员"王女士"（对应会员）**
- 基本信息：32 岁，企业职员，收入稳定，年出差/旅行 6~8 次；
- 行为特征：习惯提前 3~7 天在手机上订房，看重位置、真实房价与可取消政策；
- 核心需求：选定日期后能**立即看到有无空房与总价**，下单流程短、确认快；
- 痛点：最烦"下单后被告知没房"、到店后房型与描述不符；
- 目标与动机：快速、确定地锁定房间，行程变动时能按规则免费取消。

**画像二：忙碌的前台接待员"小李"（对应 RECEPTIONIST）**
- 基本信息：24 岁，酒店前台，三班倒；
- 行为特征：高峰期同时接待多位到店客人，需要一眼看清房态盘；
- 核心需求：按订单快速排房、办理入住登记与退房结账；
- 痛点：电话预订与线上预订可能冲突导致重房；退房后忘记改房态影响再次售卖；
- 目标与动机：房态与订单自动联动，减少手工核对，避免开错房被投诉。

## 3. 用户故事（User Story，遵循 INVEST 原则）

| 编号 | 用户故事 | 验收要点（可测试） |
| --- | --- | --- |
| US-01 | 作为一个**游客**，我想要按入住/离店日期查询各房型的**可售间数和总价**，以便于判断能否预订 | 未登录可查询；返回每房型区间内每夜可售量与 N 晚总价 |
| US-02 | 作为一个**会员**，我想要用手机号+验证码/密码注册登录，以便于下单 | 手机号唯一；登录返回访问令牌；错误凭证被拒绝 |
| US-03 | 作为一个**会员**，我想要选择房型、间数、日期并提交订单，以便于锁定房间 | 库存充足才允许下单；库存不足明确提示；订单号唯一 |
| US-04 | 作为一个**会员**，我想要在规定时限内在线支付，以便于确认预订 | 限时未支付自动取消并释放库存；支付成功订单转为"已确认" |
| US-05 | 作为一个**会员**，我想要在免费取消时限前取消订单，以便于行程变动时退款 | 免费取消期内取消全额退款并释放库存；超时按规则处理 |
| US-06 | 作为一个**前台**，我想要为已确认订单**排房并办理入住**，以便于客人到店快速入住 | 只能排"空闲/清洁合格"的同类型房间；入住后房态变在住 |
| US-07 | 作为一个**前台**，我想要办理退房，以便于房间重新可售 | 退房后生成费用结清状态，房态转为"待清洁"，清洁后回空闲 |
| US-08 | 作为一个**管理员**，我想要维护房型、房间与基础房价，以便于管理可售资源 | 房型/房间增删改查；停用房型不再对外可售 |
| US-09 | 作为一个**前台**，我想要看到实时**房态盘（房态表）**，以便于掌握全店房间状态 | 按楼层展示房间号、房型、当前房态、关联订单 |

> 迭代项（本期不做，预留接口/表）：会员积分商城、在线选具体房号、评价图文、优惠券、动态房价（日历房价）、多酒店/多门店、发票管理。

## 5. 核心交互逻辑（主流程）

### 5.1 在线预订主流程（C 端）
```
选择入住/离店日期与人数
        │
        ▼
查询可用房型（M3：逐夜计算可售量 + N 晚总价）
        │
        ▼
选择房型 / 间数 / 入住人信息 ──► 提交订单（M4）
        │   ┌── 库存不足：提示所选日期无足够空房，禁止下单
        │   ▼
事务内锁定/扣减区间内每夜库存 ──► 生成订单（状态：待支付，order_no）
        │
        ▼
限时支付（M5，默认 15 分钟）
   ├─ 支付成功回调 ─► 订单"已确认"，库存正式占用，发送确认通知
   └─ 超时未支付   ─► 定时任务取消订单并释放库存（状态：已取消）
        │
        ▼
到店：前台排房 + 办理入住（M6）─► 状态"已入住"，房态 在住
        │
        ▼
退房结账（M6）─► 状态"已完成"，房态 待清洁 ─► 清洁合格 ─► 空闲可售
```

### 5.2 免费取消流程
```
会员发起取消 ─► 判断当前时间是否在"免费取消时限"（入住日 18:00 前，可配置）
   ├─ 是：订单"已取消" → 全额退款（已支付）→ 逐夜回滚库存
   └─ 否：提示超出免费取消时限，走前台协商/首晚房费规则（MVP 仅记录，人工处理）
```

### 5.3 页面/接口跳转关系（后端视角）
- 浏览与可售查询无需登录；
- 下单、支付、我的订单、取消需 **MEMBER** 身份；
- 排房、入住、退房、房态盘、资源管理需 **RECEPTIONIST / ADMIN** 身份；
- 所有写操作通过统一鉴权拦截器校验令牌与角色（见 HLD 安全设计）。

## 6. 业务规则（重点，开发与测试的判定依据）

> 以下规则是酒店预订系统区别于普通电商的核心，务必逐条实现并可测试。

### 6.1 日期与计价
- BR-01 最小售卖单位为"**夜（间夜）**"：间夜数 `nights = 离店日期 − 入住日期`，必须 `nights ≥ 1`；离店日期必须晚于入住日期。
- BR-02 标准入住时间 14:00 后，标准离店时间 12:00 前（可在配置中调整）。
- BR-03 行单价取房型**基础房价**（MVP）；订单行小计 `= 单价 × 间数 × nights`；订单总额为各行小计之和。动态/周末房价为迭代项（预留 `room_rate` 扩展）。
- BR-04 最早可预订时间、最长可预订天数（如最远可订 90 天）由配置项控制。

### 6.2 库存与防超卖（最高优先级）
- BR-05 库存粒度为"**房型 × 日期 × 可售间数**"（见 DBD 的 `room_inventory`），而非简单的商品总库存。
- BR-06 某房型在 `[入住日, 离店日)` 区间内**每一夜都必须满足** `可售间数 ≥ 预订间数`，任一夜不足则整单不可下单。
- BR-07 下单必须在**一个数据库事务**内，对区间内每个日期的库存行执行**条件扣减**：
  `UPDATE room_inventory SET booked_count = booked_count + ? WHERE room_type_id=? AND inventory_date=? AND total_count - booked_count >= ?`；
  受影响行数为 0 即代表该夜库存不足，**回滚整单**并返回"库存不足"。以此在并发下杜绝超卖。
- BR-08 订单取消（含超时取消）/退款成功后，必须在同一事务内**逐夜回滚** `booked_count`。
- BR-09 物理房间在排房后，其占用区间不得与其他已排房订单重叠（区间重叠判定：`已入住 < 新离店 AND 新入住 < 已离店`）。

### 6.3 订单状态机
- BR-10 订单状态枚举：`PENDING_PAYMENT 待支付`、`CONFIRMED 已确认`、`CHECKED_IN 已入住`、`COMPLETED 已完成`、`CANCELLED 已取消`、`NO_SHOW 未到店`、`REFUNDING 退款中`、`REFUNDED 已退款`。
- BR-11 合法流转（其余跳转一律拒绝）：
  - 待支付 → 已确认（支付成功）／已取消（用户取消或超时）
  - 已确认 → 已入住（前台办理）／已取消（免费取消）／NO_SHOW（过入住日未到，夜间任务）／退款中→已退款
  - 已入住 → 已完成（退房）
- BR-12 待支付订单保留时长默认 15 分钟，由定时任务扫描超时单并释放库存。

### 6.4 房态
- BR-13 物理房间状态：`VC 空闲可售(Vacant Clean)`、`VD 待清洁(Vacant Dirty)`、`OC 在住(Occupied)`、`OOO 维修停用(Out of Order)`。
- BR-14 联动规则：排房入住 → OC；退房 → VD；清洁完成 → VC；维修中 → OOO（OOO 房不可排房、不计入可售）。

### 6.5 取消与 No-show
- BR-15 免费取消时限默认"入住当日 18:00 前"，配置化；超时取消的退款规则 MVP 走人工，系统仅记录与拦截。
- BR-16 已确认订单超过入住日次日凌晨仍未办理入住，夜间任务可置为 NO_SHOW（是否回收后续夜库存由酒店规则配置，MVP 不自动回收首夜）。

### 6.6 账号与权限
- BR-17 手机号全局唯一；密码必须加盐哈希存储，禁止明文；登录返回带有效期的访问令牌。
- BR-18 采用基于角色的访问控制（RBAC）：接口按 `MEMBER / RECEPTIONIST / ADMIN` 鉴权，越权访问返回 403。

## 7. 验收标准（Definition of Done，节选）

| 编号 | 功能 | 验收标准 |
| --- | --- | --- |
| AC-01 | 可售查询 | 给定库存数据，区间内任一夜可售为 0 时，该房型显示不可订；总价 = 单价×间数×夜数 |
| AC-02 | 并发下单 | 对同一房型同一夜，并发请求数 > 可售量时，成功订单数恰好等于可售量，无超卖、无负库存 |
| AC-03 | 下单事务 | 库存扣减与订单创建要么全部成功要么全部回滚，不出现"有单无库存扣减"或"扣库存无订单" |
| AC-04 | 超时释放 | 待支付超过 15 分钟的订单被自动取消，对应夜库存被准确归还 |
| AC-05 | 取消回滚 | 免费取消后，区间内每夜 booked_count 恢复到下单前数值，订单状态为已取消/已退款 |
| AC-06 | 状态机 | 任何非法状态跳转（如待支付直接入住）被拒绝并返回明确错误码 |
| AC-07 | 排房冲突 | 为订单排房时，若所选房间在该区间已有占用，系统拒绝并提示冲突 |
| AC-08 | 房态联动 | 入住/退房/清洁后房态分别正确变为 OC/VD/VC，房态盘实时一致 |
| AC-09 | 鉴权 | 未登录访问受保护接口返回 401；角色不足返回 403；密码不以明文落库或出现在日志 |
| AC-10 | 统一响应 | 所有接口返回统一 JSON 结构 `{code,message,data}`，异常也返回该结构而非堆栈页 |
